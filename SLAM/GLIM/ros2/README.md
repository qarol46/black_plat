## [Цель](#оглавление)

Пакет трёхмерного картографирования и локализации по интегрированным данным LiDAR & IMU & RGBD-Cam --- **GLIM**. Запускается как контейнеризированный сервис в составе общего docker-compose стека платформы (см. [корневой README](/README.md)).

---

## [Структура проекта](#оглавление)

```bash
SLAM/GLIM/
├── docker
│   ├── Dockerfile                      # Образ сервиса Glim
│   └── ros_entrypoint.sh
└── ros2
    ├── glim                            # Сам алгоритм
    │   ├── cmake

    │   ├── include
    │   ├── LICENSE
    │   ├── mkdocs.yml
    │   ├── package.xml
    │   ├── README.md
    │   ├── src
    │   └── thirdparty
    └── glim_ros2                       # ROS-реализация
        ├── CMakeLists.txt
        ├── include
        ├── package.xml
        ├── README.md                   # <Вы находитесь здесь>
        ├── rviz                        # Настройка отображения в RViz
        └── src
```

Сервисы `glim-cpu` и `glim-gpu` описаны в корневом [`docker-compose.yaml`](/docker-compose.yaml) и наследуют общие extension-блоки `x-env`, `x-vol` (переменные окружения, монтирование `data/`, `dds/`, X11-сокета); `glim-gpu` дополнительно получает `x-deploy` для доступа к GPU.

Возможен запуск с вычислениями как на процессоре (`glim-cpu`), так и на видеокарте (`glim-gpu`) --- выбор режима описан ниже.

## [Запуск](#оглавление)

### Режим CPU / GPU

Какой из двух сервисов (`glim-cpu` или `glim-gpu`) выберут цели `make *-glim` / `make *-slam`, определяет переменная `GLIM_SERVICE_MODE` (значения `cpu` / `gpu`, регистр не важен; по умолчанию --- `gpu`):

```bash
# Собрать и запустить в режиме CPU
make build-glim GLIM_SERVICE_MODE=cpu
make up-glim GLIM_SERVICE_MODE=cpu

# Собрать и запустить в режиме GPU (или без переменной --- это режим по умолчанию)
make build-glim GLIM_SERVICE_MODE=gpu
make up-glim GLIM_SERVICE_MODE=gpu
```

Переменную можно не указывать при каждом вызове, а экспортировать один раз в shell (`export GLIM_SERVICE_MODE=cpu`), чтобы она применялась ко всем последующим `make`-командам в этом терминале.

### Запуск внутри контейнера
Запуск производится из корня репозитория `black_plat` --- либо через `Makefile`, либо напрямую через `docker compose`. Перед первым запуском убедитесь, что переменная `ROOT_DIR` выставлена (см. [раздел "Сборка" в корневом README](/README.md#сборка)).

#### Через Makefile

```bash
# Собрать образ glim (режим определяется GLIM_SERVICE_MODE, по умолчанию gpu)
make build-glim

# Запустить только glim (в текущем терминале, с логами)
make up-glim

# Запустить в фоне (без вывода логов)
make up-glim LOG_MODE=false

# Остановить
make down-glim

# Логи в реальном времени (укажите конкретный сервис --- glim-cpu или glim-gpu)
make logs SERVICE=glim-gpu

# Bash внутри контейнера
make shell SERVICE=glim-gpu

# Статус контейнера
make ps
```

#### Через docker compose напрямую

Замените `glim-gpu` на `glim-cpu`, если нужен режим CPU:

```bash
docker compose build glim-gpu
docker compose up glim-gpu         # с логами в терминале
docker compose up -d glim-gpu       # в фоне
docker compose stop glim-gpu
docker compose logs -f glim-gpu
docker compose exec glim-gpu bash
```

### Особенности сервиса

- `network_mode: host` --- контейнер использует сетевой стек хоста, отдельная настройка портов не требуется.
- `privileged: true` --- необходим для корректного доступа к устройствам (LiDAR, IMU и т.д.), пробрасываемым через `/dev/*`.
- `restart: always` --- контейнер автоматически перезапускается при падении.
- Используется `develop.watch`: изменения в `ros2/` (кроме `config/`) вызывают пересборку контейнера, изменения в `config/` --- синхронизацию и рестарт без пересборки. Работает при запуске через `docker compose watch`.
- При остановке контейнера (`pre_stop`) автоматически, в течение 15 секунд (`stop_grace_period`), вызывается сервис сохранения карты в `/data/maps/new_map` --- если сервис не успевает отработать за это время, карта не сохранится (см. также [раздел "Сохранение карты"](#сохранение-карты)).

## [Скрипты](#оглавление)

Каталог `data/scripts/glim/` смонтирован в контейнер как volume (см. `x-vol` в корневом `docker-compose.yaml`) и содержит вспомогательные скрипты для упрощения работы с алгоритмом. Два скрипта необходимы для запуска из контейнера, где они смонтированы в директорию /scripts.

```bash
tms@tms-Legion-Pro-5-16IRX9:~/Projects/black_plat$ tree data/scripts/glim/
data/scripts/glim/
├── enter_cont.bash
├── map.bash 
└── run.bash
```

- **`enter_cont.bash`** --- открывает контейнер внутри терминала и доступом к Х11. Нужный контейнер будет открыт автоматически;

- **`run.bash`** --- сорсит ROS 2-окружение (`/opt/ros/humble/setup.bash` и `/ros2_ws/install/setup.bash`) и запускает основную ноду `glim_rosnode` с конфигом из `/glim/config`

- **`map.bash`** --- сорсит окружение и запускает `glim_ros offline_viewer` --- GUI для просмотра и сохранения карты в формате .ply. Для этого необходимо нажать File -> Open Map -> выбрать dump директорию.

## [Настройка](#оглавление)

Все JSON-конфиги пакета лежат в `data/configs/slam/glim_config/` (два набора для разных режимов работы). Какой набор файлов подключается --- определяется `config.json` (секция `global`), которая указывает на конкретные файлы `config_*.json` для каждого модуля. Ниже --- ключевые параметры, которые чаще всего требуют правки под конкретный сенсор/железо.

### `config_ros.json` --- топики и TF

- `imu_topic`, `points_topic`, `image_topic` --- имена топиков, из которых GLIM читает данные IMU, точки LiDAR и (для extension-модулей) изображение. Обязательно проверить и привести в соответствие с реальными топиками вашего драйвера сенсора.
- `imu_frame_id`, `lidar_frame_id`, `base_frame_id`, `odom_frame_id`, `map_frame_id` --- имена фреймов TF-дерева. GLIM публикует поддеревья `map → odom → base_frame` и `imu → lidar`; эти имена должны совпадать с тем, что реально существует в вашем TF-дереве (см. также обсуждение проблемы `parent_id`/`frame_id` в разделе интеграции xsens-драйвера, если используется IMU Xsens).
- `publish_imu2lidar` --- если ветку `imu → lidar` публикует другой узел (например, статический transform из URDF), стоит выставить `false`, чтобы избежать дублирующего источника этого TF-ребра.
- `acc_scale` --- множитель для акселерометра; для сенсоров Livox типично требуется `9.80665` (данные приходят в g, а не в м/с²).
- `imu_qos` / `points_qos` / `image_qos` --- QoS-профили подписки; при пропуске сообщений или предупреждениях о несовпадении QoS в первую очередь проверяются `profile`, `reliability` и `depth` здесь.

### `config_sensors.json` --- калибровка и параметры сенсоров

- `T_lidar_imu` --- экстринсик LiDAR↔IMU в формате TUM `[x, y, z, qx, qy, qz, qw]`. Это второй по важности параметр после топиков (после `extrinsicTrans` для LIO-SAM) --- при неверном значении локализация и картографирование будут давать систематическую ошибку. В файле приведены справочные значения для нескольких типовых сенсоров --- **не использовать их без проверки на своей связке**, они зависят от конкретного крепления.
- `imu_acc_noise`, `imu_gyro_noise`, `imu_int_noise`, `imu_bias_noise` --- шумовые параметры IMU. Рекомендуется получать через калибровку (см. пакет `allan_variance_ros` в этом же репозитории --- генерирует готовый `imu.yaml` в нужном формате).

### `config_viewer.json` --- визуализация (standard/interactive viewer)

- `point_size` --- размер точки при отрисовке. При `point_size_metric: false` (по умолчанию) значение трактуется в пикселях экрана, что при плотных облаках и большом значении (например, дефолтные `10.0`) даёт эффект слипшихся "клякс" вместо разреженного облака точек. Рекомендуется уменьшить, например:
  ```json
  "point_size": 0.02,
  "point_size_metric": true,
  ```
  При `point_size_metric: true` размер задаётся в метрах и не зависит от расстояния до камеры --- это обычно даёт более предсказуемый результат, чем пиксельный режим.
- `point_shape_circle` --- `true` рисует точки как закруглённые "блобы"; при проблемах с визуальной слипаемостью точек также стоит попробовать `false` (плоские квадраты/пиксели) в дополнение к уменьшению `point_size`.
- `enable_partial_rendering` / `partial_rendering_budget` --- включает поблочный рендеринг (часть точек в кадр, накопление за несколько кадров); полезно на слабых GPU, но может давать визуальные артефакты.
- `default_z_range` --- диапазон высот для отсечения по Z при отображении; настраивается под конкретную сцену (высоту потолков/этажей).
- Параметры дублируются отдельно для секций `standard_viewer` и `interactive_viewer` --- при правке визуального поведения нужно менять обе секции, если не преследуется цель их намеренно рассинхронизировать.

### `config_preprocess.json` --- предобработка облака точек

- `downsample_resolution` (для конвенционального вокселя) и `random_downsample_target` / `random_downsample_rate` (для случайного сэмплирования, `use_random_grid_downsampling: true`) --- управляют плотностью облака перед подачей в одометрию. Слишком грубое разрешение здесь может усиливать визуальный эффект "комковатости" точек независимо от настроек `config_viewer.json`.
- `distance_near_thresh` / `distance_far_thresh` --- обрезка точек по дистанции; полезно для отсечения точек на корпусе робота или далёкого шума.
- `enable_cropbox_filter` + `crop_bbox_frame` / `crop_bbox_min` / `crop_bbox_max` --- вырезание точек внутри заданного бокса (например, для исключения частей корпуса робота из облака).

## [Сохранение карты](#оглавление)

Карта сохраняется вручную через запуск скрипта **`map.bash`**. Откроется GUI для просмотра и сохранения карты. Чтобы открыть построенную карту нужно нажать File -> Open Map -> выбрать dump директорию. Далее для экспорта карты Save -> Export Points -> выбрать директорию и имя карты в формате .ply. Раздел data/maps/ синхронизуется при создании контейнера, поэтому карту можно сразу сохранять напрямую в хранилище хоста.
